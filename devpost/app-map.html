Brickbrain — app map

You type in the LEGO sets you own. The app fetches their parts, asks a model for build ideas, and then designs a 3D model made only of the bricks you own. The piece that makes that promise true is the kernel: a pure validator that checks every proposed brick against your collection and hands the model its own mistakes to fix.

One action, end to end

Reference route — three stops

A route through the finished code, anchored on real symbols. Use it to find where a change belongs.

  1. Add a set and see the collection grow. components/SetField.tsx → app/api/sets/route.ts → rebrickable/fetchSetNormalized.ts → parts/normalize.ts The field posts a set number; the route normalizes it, asks Rebrickable for the set and its parts, and normalizeSet keeps only parts whose category the renderer can draw and whose name parses into a real footprint. Everything else is dropped here, which is why it can never be claimed later. You see: the set's name, the box part count, the buildable count, and the kernel denominator.
  2. Ask for ideas and click one. components/ChatPanel.tsx → app/api/chat/route.ts → mcp/server.ts → mcp/tools.ts → lib/loop.ts The route builds an McpServer over an in-memory transport, bound to this request's inventory, and the agent loop talks to it through callTool only. propose_ideas is what puts three clickable cards in the chat. You see: three idea cards; clicking one sends its title back as your next message.
  3. Watch the kernel judge a design. validate/validateBuild.ts (validateBuild) → lib/loop.ts (applyDropRule) → components/KernelStrip.tsx validateBuild is pure: no I/O, no model, no React. It returns violations as data, the loop feeds them back to the model, and if the model never converges applyDropRule drops the offending bricks — cascading, because removing a support orphans what it carried. You see: the strip turn red with the exact complaint, then green with the used / buildable count.

A practice to reuse

Check the model's output with a pure function, and return the mistakes as data.

The temptation with a model is to trust it and debug the prose when it is wrong. Here the model is treated as untrusted input: validate/validateBuild.ts decides legality in one pure function with no I/O, and the agent loop hands its findings back as tool results instead of exceptions — because a thrown error would end the conversation, while a returned violation lets the model correct itself. The evidence is validate/validateBuild.test.ts (one test per rule) and scripts/kernel-evidence.ts, which prints the two turns a model sees when it gets a design wrong.

The same shape works anywhere a model writes code, queries, or a plan: write the check as a pure function that returns violations, feed them back, and let the caller decide what to do with an answer that is still wrong.

Where the data comes from

Part, set and colour data comes from the Rebrickable API (free, credited as their terms require). The model provider is Google's Gemini API on its free tier. Your collection is stored only in your browser's localStorage and is sent to the server with each chat request; the server keeps none of it.
