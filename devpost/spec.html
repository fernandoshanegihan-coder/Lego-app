Build With AI: Basics  ·  Technical Spec

Brickbrain

One Next.js process, one in-memory MCP server per conversation, two outbound APIs — and a validator that turns a violation into data so Claude fixes its own design.

Status · approved Local only · no deploy Next.js + R3F In-process MCP spec.md is canonical

How this works, in one breath

The browser holds your parts and nothing else. The server holds the two API keys, reads your parts off the wire, and throws them away when the request ends. Claude's only source of bricks is the inventory attached to your message.

The unusual part: Claude can run validate_build mid-answer. It returns data, not an error — so Claude reads "you use 4 red 2×4s, you own 2" and edits in the same turn. If it can't get clean in six turns, the server drops the offending bricks and renders the rest. The canvas cannot show a brick the validator rejected.

Tools are served over MCP, so the same tool code is drivable by this app and by Claude Code, unchanged.

The request path

The collection never touches a server-side store. It rides along with each chat request and is discarded with it — which is what makes "no accounts, no database, no server-side user data" true rather than aspirational.

The correction loop

This is the mechanism the whole product rests on. A violation is returned, not thrown. A thrown error ends the agent loop; a returned violation continues it.

The occupancy grid

Every brick occupies a box on an integer grid: x and z in studs, y in plates. A plate is 1, a brick is 3. Support is checked cell by cell — one occupied cell directly beneath the footprint is enough.

Components

Stack and where it runs

Framework

Next.js + TypeScript

One process, one port. Route handlers hold both API keys, so the browser never sees them. Accepted tradeoff: more framework than a single page needs.

3D

three.js · R3F · drei

The build is a list; the scene is a map over it. Layer-by-layer reveal is a slice. drei gives orbit controls and studio lighting.

Tools

@modelcontextprotocol/sdk

Real MCP over InMemoryTransport. Tool schemas are listed from the server, so each tool is described in exactly one place.

Model

@anthropic-ai/sdk

Hand-rolled loop, ~40 lines. Streaming, explicit, and it makes the MCP mechanism visible — which is the point.

Runtime

Local only

Node 20+, two keys in .env.local, npm run dev, open localhost:3000. No deploy, no database, no Docker.

Tests

Vitest

The validator is pure functions — one test per violation type, plus name parsing, rotation, and support math.

Check first thing in the build

Model ID. One constant in lib/anthropic.ts. Default to the cheapest current Haiku-class model.

SDK helper paths. The plan doesn't depend on them — the loop is hand-rolled — but verify before importing.

Rebrickable category IDs. Fetched at runtime. Confirm the bricks/plates/tiles/slope allowlist against a real set.

Data

Persisted · localStorage

The collection

Sets, and within each, only the buildable parts. The pool is derived on read by aggregating quantities across sets by (partNum, colorId).

StoredSet {
  setNum, name,
  totalParts,      // box count
  buildableParts,  // renderable
  parts: StoredPart[]
}
StoredPart {
  partNum, name, category,
  w, d,            // studs
  h,               // plates
  colorId, colorName, quantity
}
In memory only

The build

React state. Reload and it's gone — the collection persists, the build does not. That was a deliberate call, not an oversight.

PlacedBrick {
  id, partNum, colorId, colorName,
  x,  // studs
  y,  // plates
  z,  // studs
  rot // 0 | 90 | 180 | 270
}

The inventory is posted fresh with every chat message. The server retains none of it — no session, no cache, no user row.

What breaks, and what the user sees

Most likely

The set has nothing renderable

"21328 loaded, but none of its 1,234 parts can be drawn." The set is not added. Better an honest refusal than an empty shell.

The interesting one

Claude can't get clean in six turns

Three-strike rule: drop the offending bricks, render the rest. Strip reads "12 bricks dropped — they weren't in your collection."

Malformed output

Bad JSON, or a non-integer coordinate

zod rejects it inside the tool call and returns the schema as a tool result, so Claude retries. Two failures → one plain line in the chat.

External

Anthropic unreachable or key rejected

A single line in the chat. Canvas and collection untouched. The page never white-screens.

Browser

localStorage unavailable or full

The app runs, the collection doesn't persist. One notice, once.

Rate limit

Rebrickable 429

One retry after 2s, then an inline error under the field.

What was simplified

Procedural geometry instead of the LDraw library

Studs, bevels, and slopes drawn in code. This makes the renderer's vocabulary and the validator's vocabulary the same set — a part that can't be drawn can't enter the pool. The fuller version needs a ~100MB asset library, a Rebrickable→LDraw mapping table, and handling for parts with no model. A day minimum, and the kind of integration that silently eats two.

In-process MCP server instead of a stdio subprocess

No process lifecycle, no cross-process context passing, same protocol. The stdio adapter still ships, so a judge can point Claude Code at the same tools.

A hand-rolled loop instead of the SDK's toolRunner

Explicit, streamable, ~40 lines. The helper would hide the exact mechanism this project exists to demonstrate. It also keeps the loop transport-agnostic: it only ever calls mcpClient.callTool.

localStorage instead of a database

No accounts, no server-side user data, nothing to deploy. The fuller version needs auth, a schema, and a per-user hosting cost.

Slopes support nothing

A slope occupies its full bounding box and no brick may rest on its angled face. Real LEGO allows a stud on the tall edge; modelling that correctly would complicate the support rule for a rare case. Conservative is fine.

The one useful unknown

How does validate_build make Claude fix itself?

The learner's stated goal was to understand MCP; the concrete uncertainty was why this doesn't need a retry system bolted on afterwards. Clarified by the trace in Fig. 2: the tool returns { ok: false, violations } as ordinary tool output, so the model reads it in the same turn and edits. A thrown error would have ended the loop instead.

Evidence the build must produce: a recorded session where Claude's second validate_build call passes after a first one failed.
