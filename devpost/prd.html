Features and behavior

Adding a set

A dedicated field, so the app always knows that text is a set number and never a message. The app fetches the set's parts from Rebrickable, adds them to the collection, and confirms in the field with the set's name and part count.

  • Entering a valid set number shows its name and part count in the field, and the collection total rises
  • The collection summary shows the number of sets and total parts
  • Adding a set already in the collection does not increase the total
  • The set's parts are available to Claude on the next message
Asking for ideas

Exactly three ideas, grounded in the parts actually in the collection. Each is a title plus a short description. Text only — no previews. Clickable rows in the chat.

  • Asking with a populated collection returns exactly three ideas
  • Each idea shows a title and a description
  • Each idea can be clicked to proceed
  • With a collection of only tiny plates, the reply says the parts can only make small abstract shapes
Designing in 3D

Clicking an idea sends it to Claude, which returns the build as structured brick data the app renders. Bricks appear layer by layer, so the build assembles itself on screen. Size scales with the collection — one set → ~30–60 bricks, five sets → ~150–250.

  • Clicking an idea produces a 3D model built from the collection's parts
  • Bricks appear progressively rather than all at once
  • The model can be rotated
  • The counter updates as bricks are placed and ends showing used and available counts
The inventory guarantee — the kernel

The app cannot display a brick the user does not own. Three layers, and visible to the user.

  1. The prompt contains only the user's parts — Claude is never told about a part outside the collection.
  2. validate_build checks every brick — part exists, colour matches, quantity within stock, sits on the stud grid with support underneath.
  3. Invalid bricks are dropped — if Claude exhausts its attempts, the offending brick is removed rather than rendered.
  • Every brick in the rendered model corresponds to a part in the collection
  • A quantity overrun is reported to the user in the kernel strip before it is resolved
  • A colour the user does not own is never rendered
  • The final count of used parts never exceeds the collection total
Refining

The user describes a change in plain language; the design updates and is revalidated against the collection.

  • “make it taller” produces an updated model
  • The refined design is revalidated against the collection
  • The counter reflects the updated build
The collection

The user's sets live in the browser and survive a page reload.

  • Closing and reopening the page keeps the collection
  • The collection summary reflects the saved sets

States and boundaries

First use

Nothing added yet

Empty canvas, greeting in the chat, empty collection summary.

Too early

Asked before adding a set

Claude replies that it needs a set first. Canvas stays empty.

Bad input

Invalid set number

Inline error under the input box. Field keeps the text; collection and chat unchanged.

Failure

Claude or the API fails

Error appears in the chat. Canvas and collection unchanged. The page never white-screens.

Violation

Claude reaches for a brick you don't own

Kernel strip flashes the specific problem, Claude corrects itself, brick resolves or is dropped.

Honest limit

Parts too poor to build anything

Claude says so plainly and offers what is possible.

Persistence

The collection survives. The current chat and the current build do not.

Product decisions

A dedicated set-number fieldKeeps the chat purely conversational and makes adding a set unambiguous.
Inline error under the fieldThe error belongs next to the input that caused it.
Errors in the chatAPI and Claude failures surface where the conversation is; the page must stay usable.

Boundary

Deferred from the POC
  • Accounts and cloud-synced collections — the audience is students and the brief is explicit: no sign-ups. Also removes an auth provider, a database, and a per-user hosting cost.
  • Preview images for suggestions — cut to keep the build inside the time budget.
  • A deployed instance — optional; a local run and a public repo are what is required.
  • More part geometries than standard bricks and plates — slopes, wedges, round bricks, and printed parts are a large data job of their own.
  • Saving designs beyond the current session — the collection persists; the build does not.
  • Usage caps — the API costs per token. Fine at demo scale; a real product needs a cap before real traffic.
Non-goals
  • No image-to-brick generation. Photo → mosaic is a computer-vision problem in its own right. Claude composes the model rather than deriving it from a photo.
  • No PDF build guides, parts lists, or GIF export. Not needed to prove the kernel or the core loop.
  • No claude.ai as the chat client. The chat lives on this page; the user never leaves the site.
  • No purchases, pricing, or store. Out of scope for a proof of concept.
  • No accounts, sign-in, or shared collections.
  • No mobile-first layout. The demo is a desktop experience.
Possible later enhancements
  • Register the MCP server so Claude Code and claude.ai can drive the builder.
  • A parts-list and build-instructions export.
  • “Buy the missing parts” — surface BrickLink / BrickOwl links for the shortfall.
  • Multiple designs side by side for the same collection.
  • More part geometries and printed part images.
