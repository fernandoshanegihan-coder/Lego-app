Brickbrain.

Ask an AI what you can build from the LEGO sets you already own, and watch it design it in 3D — using only the exact bricks you have.

The unique kernel

The app cannot show a brick the user doesn't own. Every brick is validated against their inventory before it renders — and if the model cheats, the offending brick is dropped rather than displayed.

A design that looks right but uses parts you don't own is worthless to the person trying to build it. This project doesn't ask Claude for a build — it asks for one constrained to a specific pile of bricks, then proves it.

Who it's for

The audience

Creative students who want to build something new

They own LEGO sets — or the parts from sets they've taken apart — and want to make something original without spending money on more bricks.

The problem today

The parts list costs more than the hobby is worth

They scroll BrickLink for parts, assemble something in their head, or abandon the idea entirely. A student who can't afford the parts for a design is exactly the person for whom "build it with what you own" is the difference between making something and not.

No account needed

No Anthropic account, no subscription

The chat lives in the page. The user never leaves the site for claude.ai, and never has to sign up for anything.

Cost to us

Sub-dollar at demo scale

Rebrickable is free even commercially. Haiku 5.5 runs ≈ $0.001 per design request; a full hackathon demo lands around $1 on Haiku, $25 on Sonnet.

Boundaries

Now — in the proof of concept building now
  • Enter a set number → fetch and save that set's parts from Rebrickable
  • A growing collection — the parts pool is the union of every set added
  • No accounts, no database — collections live in the browser
  • Embedded Claude chat wired to the tools through an MCP server
  • Claude suggests ideas grounded in the actual inventory
  • 3D rendering — procedural brick geometry on a stud grid
  • Three-layer enforcement — prompt contains only your parts; validate_build checks every brick; invalid bricks are dropped
  • Self-correction — validate_build returns errors as a tool result, so Claude fixes its own design
  • Parts-used counter — “47 of 312”
  • Plain-language refinement — “make it taller” first to drop if long
  • Honest limits — when parts can't make a good build, Claude says so and offers what is possible
Later — worth doing, not now after the demo
  • Register the MCP server with Claude Code and claude.ai — top stretch item; roughly a config file and a README section
  • Real accounts and cloud-synced collections
  • Usage caps / paid tier once traffic makes the API bill real
  • More part geometries — slopes, wedges, round bricks, printed parts
  • Export parts list and build instructions as a PDF
  • “Buy the missing parts” — surface BrickLink / BrickOwl links for shortfalls
  • Multiple designs per conversation — explore alternatives side by side
  • Deployment — optional for the hackathon
Cut — named, with reasons not in this build
  • Image-to-brick generation — photo → mosaic, photo → sculpture. A proof of concept does one thing deeply; converting a photo into a brick layout is a computer-vision problem in its own right. Claude composes the model instead.
  • PDF build guides, parts lists, GIF export — not needed to prove the kernel or the core loop. A design the user can see, spin around, and build from is the whole point.
  • User accounts / sign-in — confirmed: “I don't want sign ups.” No auth provider, no database, no per-user cost, less friction for a reviewer — which matters when the audience is students.
  • claude.ai as the chat client — “The user doesn't need to go to claude.ai.” Free to us, but it breaks the core requirement and takes the user off the site.
  • Multi-user database — browser storage only.
  • Pricing, payments, purchase flows — out of scope for a proof of concept.
